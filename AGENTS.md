## Environment notes (read before doing VPS/SSH work)

- **A prior session (Claude Desktop + Desktop Commander MCP) had a persistent SSH output-capture failure** — `ssh.exe` produced zero output through every invocation method tried (`start_process`, `Start-Process` with redirected streams, piping to a file), even with flags that should force fast, loud failure (`-V`, `BatchMode=yes`). Root cause never found; likely related to `ssh.exe` expecting a real console/PTY that headless process spawning didn't provide. Worked around via guided manual execution (write exact commands, user runs them, pastes results back) — not solved.
- **If you're in a real integrated terminal (Claude Code, a normal shell), this problem likely doesn't apply** — test early with something harmless like `ssh <deploy-user>@144.79.132.100 "whoami"`. If it works, direct SSH execution is available and is preferable to guided manual execution.
- **PowerShell mangles embedded double-quotes nested inside a command string passed to an external program.** Hit repeatedly: a Dockerfile `ENTRYPOINT` line's quotes vanished when passed inline through a long CLI command; `curl -d "{\"email\":...}\"` through `ssh ...` produced JSON parse errors, because PowerShell's own argument-quoting collided with the nested JSON's quotes before it reached the remote shell. **Fix**: wrap the *entire* remote command in single quotes (`ssh host 'curl -d "..."'`) so PowerShell never touches the embedded double quotes. For long/complex payloads, write content to a file first and reference it (`-d @file.json`) instead of fighting nested quoting.

- **Do not resurrect the Aiven/CloudAMQP/third-party-cloud-free-tier path.** Explored and deliberately abandoned in favor of the user's own VPS (no credit card available). Don't re-propose it without a genuinely new reason.

## Verification discipline (the single most important habit in this project)

- **A build succeeding or a service starting is not proof a feature works.** Only exercising the actual behavior (a real request, a real response, a real failure-and-recovery) counts as verification. This project has repeatedly caught real bugs — including in Claude's own specs, not just Copilot's implementations — that a clean build alone would have missed entirely.
- **Read files directly after any AI tool (Copilot CLI, etc.) claims to have written them.** Don't trust a summary. This caught: a self-generated "VERIFICATION COMPLETE" report whose own checklist was unperformed; a security-relevant file silently rewritten to swallow all exceptions (never committed, but would have shipped if unchecked); Copilot CLI's own secret-redaction heuristic corrupting a real file's content (`Password=devpassword` → `******`) during the write itself, not just its terminal echo.
- **Test against a genuinely fresh environment, not just "it already works locally."** Two real bugs (EF migrations breaking after a refactor, a Docker Compose cold-start race) only surfaced when testing against a truly empty database / freshly created containers — an already-populated environment can mask a broken first-run experience indefinitely.
- **A build succeeding in dev mode is not proof it succeeds in production.** `npm run dev` (esbuild, lenient) has masked errors that `npm run build` (`tsc -b`, strict) caught. Run the real production build before assuming deployment-readiness.
- **Scope credentials to the minimum needed, every time.** A GitHub PAT for VPS image pulls initially defaulted to `repo` (full read/write) + `write:packages` — caught before use, corrected to `read:packages` only with an expiration set.

## Known Gotchas — general engineering lessons from this project

- NuGet defaults to the latest major package version even on a .NET 8 project — always pin explicitly. This has bitten multiple packages, not just one: EF Core packages (`8.0.*` wildcards silently drifting), `RabbitMQ.Client` (needed `6.8.1` pinned to avoid a newer major version's breaking changes), and `Microsoft.Extensions.Http`/`System.Net.Http.Json` (found pinned to `10.0.10` — a .NET 10 version — inside a `net8.0` project). Check *all* package versions against the target framework, not just the ones causing visible errors.
- Docker Compose port mapping is `hostPort:containerPort` — container-side must match what the software inside actually listens on, regardless of the host-side port chosen.
- **CORS + `UseHttpsRedirection()`**: local dev with frontend/API on different ports needs explicit CORS config. `UseHttpsRedirection()` breaks plain-http frontend calls if left in for local dev.
- **JWT claim remapping**: ASP.NET Core's JWT Bearer middleware silently renames claim types like `sub` by default. Set `options.MapInboundClaims = false` explicitly rather than working around it with manual token re-parsing.
- **AI-assisted dev failure mode**: when an AI coding tool hits an error, it tends to patch the symptom locally (add a fallback, catch-and-retry) rather than diagnose the root cause. Review AI-written code deliberately for this pattern.
- **Always use `import type { }` for TypeScript interfaces/types**, never plain `import { }`. Vite's dev-mode transform (esbuild) processes files individually and doesn't always reliably elide type-only imports, causing a runtime `SyntaxError` for something that's actually just a compile-time construct.
- **Extracting a shared library: move files, don't copy them.** Leaving originals in place after a move creates an orphaned duplicate that can compile silently (C# allows identical class names in different namespaces) — only caught by reading the file tree directly, not by trusting a successful build.
- **AI model version strings go stale fast.** Always verify current model availability via live search rather than assuming prior knowledge is current, especially for fast-moving AI provider APIs.
- **`Start-Process -NoNewWindow` requires an attached console.** Fails silently (`$null`) when launched headlessly. Use `-RedirectStandardOutput`/`-RedirectStandardError` to log files instead for scripts that might run outside an interactive terminal.
- **Don't mistake test timing for a bug.** Polling too soon after triggering an async operation can show a stale intermediate state that looks alarming but is just normal latency.
- **EF Core migrations assume the `DbContext` and its migrations live in the same assembly by default.** Splitting them across projects silently breaks migration discovery unless `.MigrationsAssembly("...")` is explicitly configured. Verify with `dotnet ef migrations list` against a genuinely fresh database, not an already-populated one.
- **`depends_on: condition: service_healthy` in Docker Compose is necessary but not always sufficient.** A healthcheck can report "healthy" slightly before the service is truly ready for new connections — don't rely on compose-level health gating alone for critical startup dependencies; add retry logic in the app itself too.
- **A "test" stage in CI is meaningless with zero real tests.** `dotnet test` (or equivalent) against a project with no test files succeeds trivially, giving false confidence.
- **Read existing operational documentation before touching shared infrastructure.** Surfaced facts (pre-existing wildcard DNS/TLS, containerized nginx) that materially changed a deployment plan — each was verified live before being relied on, never trusted blindly from the doc's prose alone.
- **When integrating with a live server hosting an unrelated project, look for a purely additive path before assuming you need to edit shared config.** Discovering the actual (non-default) Docker network name via `docker network ls` made an `external: true` network reference in *this* project's own compose file sufficient — zero lines changed in the other project's files.
