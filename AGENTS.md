# Agent Instructions — AI Job-Search Copilot

> This file is auto-read by coding agents (Claude Code, etc.) at session start. It covers **how to work in this repo** — tooling quirks, workflow rules, standing constraints. For **project state** (what's done, what's next), read `docs/HANDOVER.md`. For **why** each decision was made, read `docs/ARCHITECTURE_CONCEPTS.md`.

## Environment notes (read before doing VPS/SSH work)

- **A prior session (Claude Desktop + Desktop Commander MCP) had a persistent SSH output-capture failure** — `ssh.exe` produced zero output through every invocation method tried (`start_process`, `Start-Process` with redirected streams, piping to a file), even with flags that should force fast, loud failure (`-V`, `BatchMode=yes`). Root cause never found; likely related to `ssh.exe` expecting a real console/PTY that headless process spawning didn't provide. Worked around via guided manual execution (write exact commands, user runs them, pastes results back) — not solved.
- **If you're in a real integrated terminal (Claude Code, a normal shell), this problem likely doesn't apply** — test early with something harmless like `ssh <deploy-user>@<vps-host> "whoami"`. If it works, direct SSH execution is available and is preferable to guided manual execution.
- **Docker Desktop is installed on `D:`, not `C:` — both the app and its data.** C: was running low on space. Current layout: app at `D:\Docker\DockerDesktop`, WSL data root at `D:\DockerData` (holds both `disk\docker_data.vhdx` and the docker-desktop distro's `main\ext4.vhdx`), and `%USERPROFILE%\.docker` is a **junction → `D:\Docker\dot-docker`** (CLI plugins/config, ~384 MB). Under 6 MB of Docker remains on C:, none of it growing with usage.
  - **Don't "repair" the `%USERPROFILE%\.docker` junction** — the CLI plugins (`docker compose`, `docker buildx`) load through it and were verified working after the move. Note that an agent may be blocked from moving this directory by a credentials-handling guard (it contains `config.json` with registry auth); that's expected — have the user run the `Move-Item` + `New-Item -ItemType Junction` pair themselves.
  - **Set this at install time via installer flags — the settings file does not work.** `"Docker Desktop Installer.exe" install --quiet --accept-license --backend=wsl-2 --installation-dir=D:\Docker\DockerDesktop --wsl-default-data-root=D:\DockerData`. Both flags were verified to be honored.
  - **`DataFolder` in `%APPDATA%\Docker\settings-store.json` is silently ignored.** Docker Desktop preserves the key when it rewrites the file (so it looks accepted) but recreates the disk on C: anyway. Don't rely on it. A directory junction at `%LOCALAPPDATA%\Docker\wsl\disk` also works as a retrofit if reinstalling isn't an option, but the installer flags are cleaner.
  - **Before uninstalling Docker, remove any junction pointing into `D:` first** (`cmd /c rmdir <link>`, which never follows the link) so the uninstaller can't recurse into the real data. A reinstall over an existing `--wsl-default-data-root` **reuses the existing `docker_data.vhdx`** — images and volumes survive.
- **PowerShell mangles embedded double-quotes nested inside a command string passed to an external program.** Hit repeatedly: a Dockerfile `ENTRYPOINT` line's quotes vanished when passed inline through a long CLI command; `curl -d "{\"email\":...}\"` through `ssh ...` produced JSON parse errors, because PowerShell's own argument-quoting collided with the nested JSON's quotes before it reached the remote shell. **Fix**: wrap the *entire* remote command in single quotes (`ssh host 'curl -d "..."'`) so PowerShell never touches the embedded double quotes. For long/complex payloads, write content to a file first and reference it (`-d @file.json`) instead of fighting nested quoting.

## Standing rules — do not violate without explicit confirmation

- **Do not re-edit the co-hosted production app's own `docker-compose.yml` or nginx config.** This project shares a VPS with a live, unrelated production app. The whole point of the external-Docker-network approach (see `docs/ARCHITECTURE_CONCEPTS.md`, Step 33) was avoiding any need to touch that project's files. If a task seems to require it, stop and confirm with the user first.
- **Do not resurrect the Aiven/CloudAMQP/third-party-cloud-free-tier path.** Explored and deliberately abandoned in favor of the user's own VPS (no credit card available). Don't re-propose it without a genuinely new reason.
- **Always validate before touching shared/live infrastructure.** For nginx specifically: `nginx -t` (or the container equivalent, `docker exec <other-app>-nginx nginx -t`) before every `-s reload`, no exceptions.
- **Never put real secrets in this git repo.** Production values (VPS `.env`, API keys) live only on the VPS or in local `user-secrets` — reference via `${VAR}` in committed compose files, document *which keys exist* in `docs/HANDOVER.md`, never the values.

## Verification discipline (the single most important habit in this project)

- **A build succeeding or a service starting is not proof a feature works.** Only exercising the actual behavior (a real request, a real response, a real failure-and-recovery) counts as verification. This project has repeatedly caught real bugs — including in Claude's own specs, not just Copilot's implementations — that a clean build alone would have missed entirely.
- **Read files directly after any AI tool (Copilot CLI, etc.) claims to have written them.** Don't trust a summary. This caught: a self-generated "VERIFICATION COMPLETE" report whose own checklist was unperformed; a security-relevant file silently rewritten to swallow all exceptions (never committed, but would have shipped if unchecked); Copilot CLI's own secret-redaction heuristic corrupting a real file's content (`Password=devpassword` → `******`) during the write itself, not just its terminal echo.
- **Test against a genuinely fresh environment, not just "it already works locally."** Two real bugs (EF migrations breaking after a refactor, a Docker Compose cold-start race) only surfaced when testing against a truly empty database / freshly created containers — an already-populated environment can mask a broken first-run experience indefinitely.
- **A build succeeding in dev mode is not proof it succeeds in production.** `npm run dev` (esbuild, lenient) has masked errors that `npm run build` (`tsc -b`, strict) caught. Run the real production build before assuming deployment-readiness.
- **Scope credentials to the minimum needed, every time.** A GitHub PAT for VPS image pulls initially defaulted to `repo` (full read/write) + `write:packages` — caught before use, corrected to `read:packages` only with an expiration set.

## Workflow preferences

- **User background**: experienced backend dev (ASP.NET/C# since 2010), rusty on modern frontend/cloud-native/DevOps — not a beginner. Skip beginner analogies, use direct technical language.
- **Response style**: compact, bullet-style. Terse "what & why" recaps after each step, not long explanations, unless the concept is genuinely new to the user.
- **Coding workflow**: code is written via GitHub Copilot CLI (`copilot -p "..." --model claude-haiku-4.5`, scoped `--allow-tool` permissions), invoked directly via shell access — not chat-pasted, not VS Code Copilot chat. Claude writes the spec, invokes Copilot CLI, then verifies by reading the actual files (never trust the CLI's own summary — see Verification Discipline above).
  - **Batch related file-creation into one Copilot CLI call where possible** (explicit user preference, for request/token efficiency) rather than one call per file.
  - **Avoid inlining large or quote-heavy prompts directly in a shell command** — causes argument-escaping corruption (see PowerShell gotcha above). Write the spec to a file and point Copilot at it instead.
  - For security/reliability-sensitive code specifically (auth, secrets handling, connection resilience), consider writing directly rather than delegating to Copilot CLI — this project found Copilot repeatedly introduced subtle drift in exactly this category of code.
  - Copilot CLI with only `write` permission may not reliably create new nested directories — pre-create parent directories manually first.
- **Maintain `docs/ARCHITECTURE_CONCEPTS.md` proactively, without being asked.** Every step gets an entry: Architectural Viewpoint & Arguments, Plain-Language Definitions, File Mapping. This is a standing expectation, not a one-off request.
- **Keep `docs/HANDOVER.md` current** — Completed Steps, Next Step, Known Gotchas, Future Additions — after every step, so any future session (or tool switch) can pick up cleanly.
- Working step-by-step; confirm each step before moving to the next unless explicitly told to batch multiple steps.

## Known Gotchas — general engineering lessons from this project

- NuGet defaults to the latest major package version even on a .NET 8 project — always pin explicitly. This has bitten multiple packages, not just one: EF Core packages (`8.0.*` wildcards silently drifting), `RabbitMQ.Client` (needed `6.8.1` pinned to avoid a newer major version's breaking changes), and `Microsoft.Extensions.Http`/`System.Net.Http.Json` (found pinned to `10.0.10` — a .NET 10 version — inside a `net8.0` project). Check *all* package versions against the target framework, not just the ones causing visible errors.
- Docker Compose port mapping is `hostPort:containerPort` — container-side must match what the software inside actually listens on, regardless of the host-side port chosen.
- **CORS + `UseHttpsRedirection()`**: local dev with frontend/API on different ports needs explicit CORS config. `UseHttpsRedirection()` breaks plain-http frontend calls if left in for local dev.
- **JWT claim remapping**: ASP.NET Core's JWT Bearer middleware silently renames claim types like `sub` by default. Set `options.MapInboundClaims = false` explicitly rather than working around it with manual token re-parsing.
- **AI-assisted dev failure mode**: when an AI coding tool hits an error, it tends to patch the symptom locally (add a fallback, catch-and-retry) rather than diagnose the root cause. Review AI-written code deliberately for this pattern.
- **Always use `import type { }` for TypeScript interfaces/types**, never plain `import { }`. Vite's dev-mode transform (esbuild) processes files individually and doesn't always reliably elide type-only imports, causing a runtime `SyntaxError` for something that's actually just a compile-time construct.
- **Extracting a shared library: move files, don't copy them.** Leaving originals in place after a move creates an orphaned duplicate that can compile silently (C# allows identical class names in different namespaces) — only caught by reading the file tree directly, not by trusting a successful build.
- **AI model version strings go stale fast.** Always verify current model availability via live search rather than assuming prior knowledge is current, especially for fast-moving AI provider APIs.
- **`Start-Process -NoNewWindow` requires an attached console.** Fails silently (`$null`) when launched headlessly. Use `-RedirectStandardOutput`/`-RedirectStandardError` to log files instead for scripts that might run outside an interactive terminal.
- **Don't mistake test timing for a bug.** Polling too soon after triggering an async operation can show a stale intermediate state that looks alarming but is just normal latency.
- **EF Core migrations assume the `DbContext` and its migrations live in the same assembly by default.** Splitting them across projects silently breaks migration discovery unless `.MigrationsAssembly("...")` is explicitly configured. Verify with `dotnet ef migrations list` against a genuinely fresh database, not an already-populated one.
- **`depends_on: condition: service_healthy` in Docker Compose is necessary but not always sufficient.** A healthcheck can report "healthy" slightly before the service is truly ready for new connections — don't rely on compose-level health gating alone for critical startup dependencies; add retry logic in the app itself too.
- **A "test" stage in CI is meaningless with zero real tests.** `dotnet test` (or equivalent) against a project with no test files succeeds trivially, giving false confidence.
- **Read existing operational documentation before touching shared infrastructure.** Surfaced facts (pre-existing wildcard DNS/TLS, containerized nginx) that materially changed a deployment plan — each was verified live before being relied on, never trusted blindly from the doc's prose alone.
- **When integrating with a live server hosting an unrelated project, look for a purely additive path before assuming you need to edit shared config.** Discovering the actual (non-default) Docker network name via `docker network ls` made an `external: true` network reference in *this* project's own compose file sufficient — zero lines changed in the other project's files.
- **A message queue is point-to-point; an exchange is pub/sub.** Adding a second independent consumer to a queue an existing consumer already reads from doesn't give both of them every message — RabbitMQ round-robins deliveries between them, silently halving what each one sees. The moment more than one subscriber needs the same event, the publisher needs to target a fanout (or topic) exchange, with each subscriber binding its own queue to it. Caught by reading the existing consumer's code before writing a new one, not by testing after the fact.
- **`mongodb+srv://` DNS SRV lookups can fail through Node's own resolver while the OS's resolver answers the identical query fine** (`dns.resolveSrv` failing with `querySrv ECONNREFUSED` against a network's configured DNS server, confirmed directly). A known class of issue with `mongodb+srv` specifically. Fix: set explicit public DNS servers (`dns.setServers(['8.8.8.8', '1.1.1.1'])`) before connecting — a real fix, not a workaround for one network, since it depends on the *client's* resolver behaviour, not anything MongoDB-side.
- **A TLS handshake that fails identically from two unrelated networks points at the server side, not either client.** A `SSL alert number 80 (internal_error)` connecting to MongoDB Atlas, reproduced with raw `openssl s_client` (not just the driver) from both a home workstation and, separately, the VPS, turned out to be Atlas's Network Access (IP allowlist) simply not including either source IP — Atlas's "Automate security setup" only added the one IP it detected via the browser session, which didn't match either machine's actual egress IP. When ruling out a network-path issue, test from a second, unrelated network before assuming the cause is local.
- **Bash's `**` glob only recurses with `globstar` enabled, and that's off by default in non-interactive shells** (including GitHub Actions' own script steps) even when it happens to be on in an interactive local session. A `package.json` test script like `test src/**/*.test.ts` can pass locally and fail in CI with the literal unexpanded string handed to the test runner. Don't depend on shell-glob behaviour matching across environments — pass explicit paths, or use the test runner's own directory-based discovery instead.
- **A Docker-discovery-based collector (Alloy's `prometheus.exporter.cadvisor`, `discovery.docker`, and anything built on the same pattern — Promtail, cAdvisor standalone, etc.) has no built-in project scoping.** By default it scrapes/tails *every* container on the host, not just this project's own — a real problem on a VPS shared with an unrelated co-hosted app, both because it ships someone else's data into this project's observability backend and because cAdvisor exposes one scrape target for the *whole host*, so per-container filtering can't happen at the discovery/target-relabel stage - it has to be a post-scrape `prometheus.relabel` keep rule on the per-metric `name` label. Docker log discovery is filterable pre-tail (a `keep` rule on `__meta_docker_container_name` in `discovery.relabel`), but metrics are not. Always scope both explicitly (e.g. `jobcopilot-.*`) rather than assuming a collector is naturally limited to "this project."
- **Grafana Cloud Loki rejects an entire push batch if any single entry in it is older than roughly the last 7 days** (`"timestamp too old"`), not just the old entry - so batching one container's ancient log backlog alongside another's current logs silently drops the current logs too. Docker's default `json-file` log driver keeps a container's *full* history across plain restarts (only a true recreate resets it), so even a project's own long-lived containers can trigger this on a collector's first tailing pass. Verified this is a one-time catch-up rather than a steady problem by watching the dropped-bytes counter go flat while the sent-bytes counter kept climbing - don't assume it self-resolves, check the counters.
- **A container's own embedded HTTP/API server must still bind `0.0.0.0` inside the container even when the host-side Docker port mapping is loopback-only** (`127.0.0.1:PORT:PORT`). Binding the process itself to `127.0.0.1` binds it to the *container's own* loopback, which the host-side port mapping cannot reach at all - same failure shape as the frontend nginx/`wget` `::1` vs `0.0.0.0` mismatch (Step 34), different layer.
- **A secret pasted from a screenshot/UI panel is a transcription risk, not a copy.** A Grafana Cloud API token relayed this way came through corrupted (silent, not truncated-looking) and produced a `401: invalid token` from both endpoints it was used against - config was otherwise correct, only the secret was wrong. Prefer the UI's own "copy to clipboard" over retyping or reading off a screenshot for any credential.
